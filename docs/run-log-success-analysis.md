# 运行日志成功率整理（2026-11-16）

> 数据源：收集服务 `run_logs` 表；窗口 **近 45 天**；过滤 `source <> 'manual'`（手动上传的诊断日志不计入）、
> `origin <> 'third_party'`（非官方签名包不计入）。
> 统计单位是**构建号 + 引擎**，并把「一台机器反复重试」与「多台机器」分开：主指标用
> **成功过的独立 install 数**（`ok_installs`），而不是运行次数 —— 98260 的「一次开机只跑一次」
> 和 GhostLock 的「一轮 24-30 次 attempt」都会让运行次数失真。

## 判定规则

一个「构建号 + 引擎」组合转为**已测试**，需要同时满足：

1. 近 45 天内 **≥ 3 个独立 install** 跑成功（排除同一台机器刷成功率）；
2. 整轮成功率 ≥ 40%（GhostLock）/ ≥ 50%（98260）；
3. 能用 App 里真实存在、且对该构建可选的载荷跑出来（不能靠手动改包）；
4. 有明确的机型条目或共用条目可以承载它（否则先加条目）。

反例：`S9260ZHU6EZIF` 有 5 个 install 成功，但整轮成功率只有 3.7%（134 次运行）——典型的
「偶发命中」，不转已测试。

## 说明与局限

- 日志里的 `build_tag` 来自设备指纹；个别第三方 ROM / 非三星设备的构建串是垃圾值，已按三星构建格式过滤。
- 一个构建上的成功可能来自「用户手动选了别的 profile」。本表把这种也算作「该构建可用」，
  因为它证明了载荷在该内核上能跑；但入口仍应由对应条目提供，避免用户误选 GHOSTLOCK 条目。
- 整轮成功率天然偏低（GhostLock 一轮多次 attempt、98260 parked 失败需重启），
  所以阈值按引擎区分，而不是统一卡 60%。
